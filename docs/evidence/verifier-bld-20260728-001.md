## 2. CORRECTNESS OF unified_wal_path FOR ACTIVE WAL REPORTING — VERIFIED

### 2a. unified_wal_path lifecycle

`unified_wal_path` always resolves to `wal.log` (line 209). It is never reassigned after construction (line 237). During snapshot rotation (`take_snapshot`, lines 644-694):

1. The current `wal.log` is renamed → `wal.wal.old` (line 674)
2. The previous `wal.wal.old` is removed (line 671)
3. `self.wal_file` is cleared (line 679)
4. A fresh WAL is seeded with Genesis via `persist_record()` (line 688), which opens `self.unified_wal_path` with `.create(true).append(true)` (lines 467-470), creating a new file at the now-empty `wal.log` path

**Conclusion:** `unified_wal_path` always points to the current active WAL file. Rotated data lives in `wal.wal.old` (a one-cycle fallback removed on next rotation). Reading `unified_wal_path` in `get_stats()` correctly reports the active WAL size, excluding historical `.old` files.

### 2b. Legacy wal_path is deprecated

`wal_path` (`transactions.wal`) is the legacy WAL from the pre-unified era. It is still written to via `flush_wal()` (line 270, using a handle opened at startup at line 219), but the unified WAL (`wal.log`) is the canonical WAL for recovery (line 518: `std::fs::read(&self.unified_wal_path)`). The legacy path is maintained for backward compatibility during migration and will be truncated over time (per comments at lines 514-517).

Reading `self.wal_path` in `get_stats()` was therefore reporting the size of the wrong WAL — the legacy `transactions.wal` file, not the active unified `wal.log`.
